# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Standbye: a BYOK macOS desktop app where the user describes a team of AI agents and the agents keep working on a repo around the clock. Agents check in on a schedule, talk to each other in channels, ask the owner when a decision is theirs, propose hires, and save memory and skills. Internal npm scope is `@crew/*`; the product name is Standbye.

## Commands

```bash
pnpm install
pnpm dev            # builds shared + supervisor, then electron-vite dev with hot reload
pnpm typecheck      # tsc across all packages (run this before committing; there is no linter)
pnpm test           # node --test: supervisor tests against dist/ (packages/supervisor/test/*.test.mjs) + desktop store tests (apps/desktop/test/*.test.mjs; needs node >= 22.18 for unflagged TS stripping)
pnpm smoke          # no-key end-to-end test of the supervisor (scripts/smoke.mjs)
pnpm package        # icon + bundled supervisor + macOS dmg/zip into apps/desktop/release
pnpm --filter @crew/desktop gui   # Playwright drives the real app and screenshots each screen (apps/desktop/e2e/gui.mjs)
pnpm --filter @crew/web dev       # landing page with hot reload on :5174; `build` writes apps/web/dist
docker build -f apps/web/Dockerfile -t standbye-web .   # from the repo root: nginx image of the landing page
```

- Shared types must be rebuilt before the supervisor or desktop typecheck sees changes: `pnpm --filter @crew/shared build`.
- Live tests that spend money: point OpenRouter at `z-ai/glm-5.3-flash` (`providers.set { openrouter: { defaultModel, checkinModel } }`) on a scratch data dir. Pass the OpenRouter key for tests through the environment (`OPENROUTER_API_KEY`); the repo keeps no `.env`. Set `CREW_DISABLE_CLAUDE_LOGIN=1` on a supervisor to make sure it never uses the machine's Claude Code login.
- Run the supervisor by hand: `node packages/supervisor/dist/index.js --data <dir> --port <n> --token <t>`; talk to it over WebSocket JSON-RPC (`{id, method, params}`), see `scripts/smoke.mjs` for the client shape.
- Headless UI checks: `CREW_DATA_DIR=<dir> CREW_SCREENSHOT=/path.png CREW_SCREENSHOT_QUIT=1 ./node_modules/.bin/electron .` from `apps/desktop` after `electron-vite build`.

Commit messages never mention Claude, sessions or AI assistance (owner's rule).

## Architecture

Three workspaces: `packages/shared` (types + zod schemas, the contract between the other two), `packages/supervisor` (the daemon), `apps/desktop` (Electron + React UI). A fourth, `apps/web`, is the landing page: a static Vite site that imports the desktop kit (`@kit` → `apps/desktop/src/renderer/ui`, `@kit-styles` → `styles.css`) and the starter team (`@templates` → `packages/supervisor/src/templates.ts`) straight from source via Vite aliases, so the site's mock windows are the real components. It has no runtime link to the supervisor. `apps/web/Dockerfile` builds it into an nginx image from the repo root.

**The supervisor is a separate process.** Electron spawns it with the user's `node` (found via PATH, Homebrew, nvm) and talks over a local WebSocket with a per-launch token. The supervisor writes `supervisor.json` (pid, port, token) into the data dir; a starting app attaches to a live one instead of spawning, and only stops a supervisor it started. Packaging copies a flat, symlink-free supervisor tree into the app bundle (`scripts/deploy-supervisor.mjs` + `apps/desktop/scripts/after-pack.cjs`), because electron-builder drops `node_modules` from extraResources.

**Teams are folders, and a team with a workspace belongs to the project.** `Hub` (`supervisor/src/hub.ts`) gives every team its own `Crew` (SQLite `crew.db`, `agents/<id>/{agent.json,SOUL.md,RULES.md,MEMORY.md,skills/}`, `team.json`, `skills/`) and its own `Scheduler`. That folder is `<workspace>/.standbye` when the team has a workspace, so it travels with the repo and can be committed; a team with no workspace has no project to belong to and stays in `<dataDir>/teams/<id>`. `workspaces.json` only remembers which project folders to look in — the folder itself is the truth, so a team survives being moved with its repo. `adoptProjectTeams()` moves pre-`.standbye` teams into their workspace on startup, never over an existing one. What stays global is what is this Mac's business and must not land in a repo: keys, `providers.json`, `workspaces.json`, `archived.json`, and the `<dataDir>/skills/` shelf. Events from every crew are re-emitted with a `teamId`; the API (`api.ts`) keeps a selected team per connection and the renderer store filters events to the active team.

**Being on the team list is what makes a team work.** Removing one is therefore an off switch, not a delete: `archiveTeam` stops its scheduler, records it in `archived.json` and leaves every file alone, and the constructor skips archived ids so it stays off across restarts. `restoreTeam` (or simply opening the folder again) puts it back — `load()` clears the archive record whichever way the team is reached, so a team is never both open and archived. `deleteTeam(id, removeFiles)` is the real one and works on live and archived teams alike.

**Deciding their own work.** A team that only reacts is a team you have to feed. `backlog.ts` gives it somewhere for an idea to live between being noticed and being built: `.standbye/backlog.json`, committed with the project, so a clone knows what the team was going to do next. Agents run it themselves with `add_idea`, `list_backlog`, `rank_backlog` (the lead's job), `claim_item` (refused if a teammate holds it) and `finish_item`. An idle check-in no longer just naps: `idleWork()` in `prompt.ts` sends it to finish what it already owns, take ready unclaimed work, or — when the backlog is empty — go and find what the project needs. How far they may take it is `team.autonomy`: `propose` (find and rank, ask before writing code), `pr` (build on a branch, end in a pull request — the default) or `auto` (build and land on the work branch; staging and production still gated by the git rules). It is the owner's dial, enforced by the app, stated in the prompt so an agent knows where it stands rather than so it can choose.

**Runs are the unit of work.** `Scheduler` turns time and events into runs: heartbeats every N minutes inside work hours (run on the cheap check-in model; the agent calls `escalate` to get a full run), cron triggers, and bus events (mention → run for each mentioned agent, question to an agent, task hand-off, answer to the asker, default answers when a question's deadline passes, hire approval creates the agent). `Queue` serializes runs per agent with a global concurrency cap and collapses duplicate wake-ups. `runner.ts` builds prompts (`prompt.ts`: soul, rules, team, decisions, memory, skills, plus what's new since the last run), checks budgets, dispatches to a provider runner, and records steps and cost.

**Providers are a catalog, runners are a kind.** `packages/shared/src/providers.ts` lists every way into a model the app supports (34 of them: Claude, coding-agent CLIs, coding plans, API keys, clouds, local servers) with its endpoint, auth, models, brand mark and — for a CLI — the exact headless invocation. Nothing else in the codebase names a vendor: the settings screen, the model picker, the team builder and the landing page all read this list, and adding a provider means adding an entry. `supervisor/src/providers.ts` owns `providers.json`, credential resolution (saved key → the vendor's usual env var), readiness (`ProviderState.blocker` is the one line the owner acts on), CLI discovery on a PATH that Electron truncates, and `probeProvider` behind the Test button. It also owns `ATTRIBUTION_HEADERS` (`HTTP-Referer` + `X-Title`, from `APP_URL`/`APP_NAME` in shared), sent on every billed OpenRouter call — the run loop in `runners/openai.ts` and the team builder — so a run shows up as Standbye, linked, in the owner's OpenRouter activity log instead of as an anonymous line. The public model catalog is unbilled and goes unattributed.

**Three runners, one tool surface.** `runner.ts` dispatches on the spec's `kind`, not its id. `runners/anthropic.ts` (kind `claude`) uses the Claude Agent SDK with the team tools as an in-process MCP server; `claudeEnv` points it at any Anthropic-compatible endpoint or at Bedrock/Vertex/Foundry — and clears an inherited `ANTHROPIC_API_KEY`, or a third-party run silently bills Anthropic. `runners/openai.ts` (kind `openai`) drives any OpenAI-compatible base URL through the AI SDK `ToolLoopAgent` with the same team tools plus `runners/workspace.ts`'s file/shell toolset. `runners/cli.ts` (kind `cli`) spawns somebody else's headless coding agent and, where the CLI takes an MCP server on the command line, hands it `mcp/stdio.js` so it joins the team properly; where it does not, the run is one-shot and its last paragraph becomes the summary. The first two route file and shell tools through `runners/approval.ts`: a workspace fence, then allow/ask/block rules from `permissions.ts`; "ask" files an approval question and blocks the tool call until the owner answers or it times out. A spawned CLI brings its own tools and is bounded by the workspace it is pointed at and the run timeout. `tools/team-tools.ts` is the single definition of what agents can do to each other and to the owner; `mcp/stdio.ts` exposes the same tools as a stdio MCP server that proxies to the API so external clients (Claude Code, a spawned CLI) can act as a teammate.

**Cost.** OpenRouter reports the real figure and Claude Code reports its own; everyone else is priced from `pricing.ts` against the catalog and whatever the live model list added. A flat-rate coding plan or a model on this Mac costs 0, which is the truth — there the turn cap and the run timeout are the ceiling, not the budget.

**Skills are folders in the Agent Skills format** (`skills.ts`). One folder per skill, holding a `SKILL.md` whose YAML frontmatter carries `name` and `description`, plus optional `scripts/`, `references/` and `assets/` — the agentskills.io standard, so a Claude Code skill drops straight in and one written here works anywhere else. Three shelves, most specific wins on a name collision: `<dataDir>/skills/` (every team), `teams/<id>/skills/` (that team), `teams/<id>/agents/<id>/skills/` (that agent). `SkillLibrary` on each `Crew` owns reading, writing, install (local folder, zip, git/GitHub shorthand, or Claude Code's own folders — `skillOrigins()` finds them), `update` (re-pull from the recorded source in `.standbye-source.json`) and `move` between shelves. Only the name and description are ever in a prompt: the Claude runner mounts the agent's skills as a generated local plugin (`buildPlugin` → `<agentDir>/.skillset`, symlinks, skills addressed as `skills:<name>`) and lets the SDK's Skill tool open them; every other model gets the catalog in its prompt and reads one with `use_skill`. `agent.disabledSkills` is the owner's per-agent off switch. Legacy flat `skills/<name>.md` files are migrated into the folder format on first read.

**The user shelf starts full.** `packages/supervisor/skills/` holds the 24 skills Standbye ships with — the craft (getting oriented, shipping a change, reviewing one, writing tests, debugging, refactoring, fixing a red build, running a spike, making it faster, updating dependencies, git, GitHub, docs, triage, secrets, security review), and how to behave on this team (asking the owner, working with teammates, planning the work, staying inside budget, working safely, remembering and learning, writing a status report, growing the team) — and `syncBundledSkills` (`bundled-skills.ts`, called from the `Hub` constructor) copies them onto `<dataDir>/skills/` the first time a supervisor starts, so a fresh install has a team that already knows how to behave. After that they are the owner's: a folder deleted here stays deleted (`<dataDir>/bundled-skills.json` remembers we installed it once), an edited copy is never overwritten (`.standbye-source.json` records the hash we wrote, so any other content means a person changed it), a name the owner's own skill already uses is left alone, and only an untouched copy is refreshed when the shipped version moves on. `scripts/deploy-supervisor.mjs` copies the folder next to `dist/`, which is how `bundledSkillsDir()` finds it in both the repo and the packaged app.

**Team builder** (`builder.ts`) turns a description into a `TeamDraft` via whichever backend is ready: Anthropic API key (Messages API JSON schema), Claude Code login (Agent SDK `outputFormat`), or any OpenAI-compatible key (AI SDK `Output.object`). A coding CLI or a cloud cannot draft — shelling out and hoping for clean JSON is worse than the template — but the team it produces can run on them. `templates.ts` holds the solo dev team; `adaptToProviders` moves every agent onto a provider that is actually ready before the team is created, so a machine with only a Copilot seat still gets the starter team.

**The app updates itself, because nothing is signed.** `main/updates.ts` asks the GitHub Releases API for the latest release, compares it to `app.getVersion()`, and picks the one asset this platform and architecture can install over itself — the macOS `.zip` (not the `.dmg`), the Windows NSIS `setup.exe`, the Linux AppImage but only when running from one. electron-updater is not used: its macOS path goes through Squirrel.Mac, which refuses to install over an unsigned bundle, and unsigned is what we ship. Download and unpack happen while the app is running so a failure is something the owner can be told about; the swap itself is a detached `/bin/sh` script that waits for our pid to exit, because a process cannot replace the bundle it is executing from. `autoUpdate` in `app-settings.json` defaults to **on** and only ever means "fetch it": installing happens on the Restart button or in `before-quit`, never while the owner is working. A `.deb`, a dev run or a release with no matching file sets `canInstall: false` and the release page is all that is offered. The whole state (`UpdateState` in shared) is pushed to the renderer on `crew:update`, and the sidebar row, the tray and Settings → Updates all render that one object.

**Renderer** (`apps/desktop/src/renderer`): one external store (`state/store.ts`, `useSyncExternalStore`) holds everything and receives pushes from the supervisor via preload IPC. Store selectors must return stable references while data loads (use module-level empty constants), or the screen re-renders forever. UI is a native macOS-style kit (`ui/kit.tsx`, `styles.css`): sidebar, toolbar, table rows, inspector, sheets centered in the window. Overlays (model picker, team switcher) render through a portal with fixed positioning so nothing clips or causes horizontal scroll. Screens live in `screens/`; the design they follow is in `design/*.dc.html`.

## Conventions worth knowing

- Every limit is enforced by the app, not the model: permission rules, per-agent budgets (day / rolling hour / per run), team daily cap, chat-depth cap on agent-to-agent mention threads, a runs-per-hour ceiling that the owner's own messages bypass, work hours.
- `decide()` resolves ties toward the most restrictive rule. Do not "fix" that: an equally specific allow used to beat a force-push block.
- Reports (`ask_user` with `kind: "report"`) land in the inbox without blocking the agent; questions and approvals do.
- `remember` appends to MEMORY.md and is loaded into every subsequent run. `learn_skill` writes a skill folder (the agent's own shelf, or the team's with `scope: "team"`); from then on only its name and description are in the prompt, and the agent opens it with `use_skill`. Decisions the owner marks "remember" are shown to all agents so nobody re-asks.
- The template lead ships with three schedules (weekday standup, end-of-day report, Friday retrospective); the builder is told to add the same.
